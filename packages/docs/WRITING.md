# Writing the Jimp docs

This is the guide for anyone adding or editing pages on the docs site
(`packages/docs`). It covers where things live, how pages are structured, the
tone to write in and how to check your work.

The site is [Astro](https://astro.build) + [Starlight](https://starlight.astro.build)
with a custom theme ("Kid Studio", plus a "Night Studio" dark mode). The look
comes from the theme and components; page content stays plain Markdown/MDX.

## Where things live

| Path                                     | What it is                                                                   |
| ---------------------------------------- | ---------------------------------------------------------------------------- |
| `src/content/docs/index.mdx`             | Home page                                                                    |
| `src/content/docs/guides/*.mdx`          | Guides: task-oriented walkthroughs                                           |
| `src/content/docs/concepts/*.mdx`        | Concepts: how Jimp works                                                     |
| `src/content/docs/methods/index.mdx`     | The method index (sticker sheets)                                            |
| `src/content/docs/methods/<slug>.mdx`    | One page per method or helper                                                |
| `src/content/docs/api/`                  | Generated by starlight-typedoc at build time. Never edit; it's git-ignored. |
| `src/data/methods.ts`                    | Every method page: slug, API name, category, package. Drives the sidebar.    |
| `src/data/pages.ts`                      | Guides and concept pages, in sidebar order                                   |
| `src/data/categories.ts`                 | Method categories (labels and sticker colors)                               |
| `src/sidebar.ts`                         | Builds the sidebar from the data files                                       |
| `src/components/playground/`             | The live playground, sticker sheet and the op registry                      |
| `src/components/playground/ops/*.ts`     | Playground ops, one file per area                                            |
| `src/overrides/`                         | Starlight component overrides (header, sidebar, page title, TOC…)           |
| `src/styles/`                            | Design tokens and global styles                                              |
| `public/`                                | Static files. `dice.png` is the playground's default image.                 |

### Shared files

The sidebar, data files, overrides, styles and the playground engine
(`Playground.tsx`, `StickerSheet.tsx`, `Controls.tsx`, `registry.ts`,
`types.ts`, `code.ts`, `images.ts`) are shared by every page. When several
people are writing pages at once, don't edit them: work only in your own pages
and your own `ops/*.ts` file. If you need a change to a shared file, ask for it.

Every method and concept page already exists as a stub with its frontmatter
filled in, and the sidebar already lists it. Replace the `{/* TODO */}` body.

## Tone

- Write clear, accurate technical documentation. The personality comes from
  the visuals, not the prose: no jokes, puns, exclamation marks or emoji.
- Use plain, direct sentences in the second person ("Pass `w` to set the
  width."). Prefer short sentences and one idea per paragraph.
- Use the real API names, in code formatting: `image.resize()`, `Jimp.read`,
  `ResizeStrategy.BICUBIC`. Don't invent methods, options or defaults.
- Check every claim against the source in `packages/` and `plugins/`. Option
  names, defaults and error messages must match the code exactly. When the
  source and an old doc disagree, the source wins.
- Say what something does before how it works. Lead with the common case;
  put edge cases in **Notes**.
- Use US spelling in prose (color, gray, center). Method names keep their
  own spelling, such as `greyscale`.

## Code samples

- Every sample must be valid Jimp v1 and runnable as written (apart from file
  names). Import what you use: `import { Jimp } from "jimp";`.
- Use the v1 API: options objects (`resize({ w: 100 })`), promises for
  `Jimp.read`, `getBuffer`, `getBase64` and `write`, named exports for
  constants (`ResizeStrategy`, `BlendMode`, `JimpMime`…).
- Give code blocks a filename title so they get the sticker tab:
  ` ```ts title="example.ts" `. Use `sh` for shell commands.
- Short continuation snippets (a few lines that build on the previous
  example) may skip the import and read, as long as `image` is clearly a Jimp
  image from the example above.
- Run new samples before publishing. From `packages/docs`, a scratch file can
  import the workspace build:

  ```sh
  cat > scratch.mjs <<'EOF'
  import { Jimp } from "jimp";
  const image = await Jimp.read("public/dice.png");
  image.blur(5);
  console.log(image.width, image.height);
  EOF
  node scratch.mjs && rm scratch.mjs
  ```

Version notes: when an API or option is new in a release, add a **Notes**
bullet "Added in 2.0." (with the version it shipped in). When behaviour
changed, add "Changed in 2.0: …" and say in one clause what it did before.
Don't document library bugs as intended behaviour; if you find one, note it in
an `<Aside type="caution">` and open an issue.

## Frontmatter

All pages use Starlight's fields (`title`, `description`, `sidebar`,
`prev`/`next`, `template`…) plus three custom ones defined in
`src/content/config.ts`:

| Field         | Used on      | Meaning                                                                 |
| ------------- | ------------ | ----------------------------------------------------------------------- |
| `title`       | all          | Method pages: the call, e.g. `"blur()"`, `"Jimp.read()"`, `"new Jimp()"` |
| `description` | all          | One sentence. Shown under the title, in search and on the method sticker |
| `category`    | method pages | Category id from `src/data/categories.ts`. Sets the sticker and color  |
| `method`      | method pages | The API name, e.g. `"blur"`, `"Jimp.read"`. Renders the title in code font |
| `plugin`      | method pages | npm package the API comes from, e.g. `"@jimp/plugin-blur"`              |

Keep `category`, `method` and `plugin` matching the page's entry in
`src/data/methods.ts`. Keep `description` to one sentence of about 12 words:
it's the sticker text on `/methods/`.

## Method page anatomy

`src/content/docs/methods/blur.mdx` is the finished example. Follow its order:

1. **Intro** (no heading): one or two sentences on what the method does and
   when to use it.
2. **`## Signature`**: a `ts` block titled `<name>.d.ts` with the call
   signature(s), then one sentence on whether it mutates and returns the image.
   Show option types inline (`options: { x: number; ... }`) or link to the
   type in the [type reference](/jimp/api/readme/).
3. **`## Parameters`** or **`## Options`**: a table with
   `Option | Type | Default | Description`. Write `required` in the Default
   column for required values. Use "Parameters" for positional arguments and
   "Options" for an options object.
4. **`## Example`**: a complete, runnable example. Add `###` subsections for
   other common uses.
5. **`## Try it`**: one sentence, then `<Playground method="<op id>" client:visible />`
   if the method has a playground op. Skip this section otherwise.
6. **`## Notes`**: behaviour worth knowing: edge cases, errors it throws (quote
   the exact message), performance, alpha handling, v0 differences. Use an
   `<Aside>` only for something that can bite people.
7. **`## Related`**: `<Related methods={["gaussian", "pixelate"]} />` with API
   names from `src/data/methods.ts`.

For functions that aren't image methods (`intToRGBA`, `diff`, `loadFont`…),
use the same order and show the import in the signature.

## Concept page anatomy

1. **Intro** (no heading): what the concept is and why it matters, in two or
   three sentences.
2. **`##` sections** that build from the simplest case to the advanced one.
   Each section: a sentence or two, then a short example.
3. Link every method you mention to its method page the first time:
   `[`composite`](/jimp/methods/composite/)`.
4. Embed a `<Playground>` or `<StickerSheet>` where trying something beats
   reading about it.
5. End with **`## See also`**: links to related guides, concepts and methods.

The stub for each concept page lists its intended scope in a comment.

## Components

Import components at the top of an `.mdx` file, after the frontmatter. Paths
are relative to the page.

### `<Playground>`

```mdx
import Playground from "../../../components/playground/Playground";

<!-- One method: its options only, and the code shows that one call -->
<Playground method="blur" client:visible />

<!-- Several methods as tool buttons, with a first step already applied -->
<Playground
  client:visible
  tools={["resize", "rotate", "blur", "greyscale"]}
  steps={[{ op: "resize", options: { w: 200 } }]}
/>
```

| Prop     | Type                                   | Default        |
| -------- | -------------------------------------- | -------------- |
| `method` | op id: single-method mode              |                |
| `tools`  | op ids: tool buttons (multi-tool mode) | every op       |
| `steps`  | `{ op, options? }[]` applied on load   | none           |
| `src`    | image in `public/`                     | `"dice.png"`   |
| `height` | minimum image area height in px        | `260`          |
| `flavor` | `"node"` or `"browser"` code           | `"node"`       |
| `title`  | title in the top bar                   | `"Playground"` |

Always add `client:visible`. Readers can upload their own image, undo, reset,
hold to compare with the original, download the result and copy the code.

### `<StickerSheet>`

```mdx
import StickerSheet from "../../../components/StickerSheet.astro";

<StickerSheet category="color" />
<StickerSheet methods={["blur", "gaussian", "pixelate"]} />
```

Methods with a playground op get a live thumbnail; others get an icon. The
sticker text is each method page's `description`. Don't add `client:visible`;
the component does it.

### Others

- `<Related methods={[...]} />` from `src/components/Related.astro`: pill links
  to method pages.
- `<InstallCommand pkg="@jimp/wasm-webp" />` from
  `src/components/InstallCommand.astro`: npm / pnpm / yarn tabs.
- Starlight's `<Aside type="note|tip|caution|danger">`, `<Steps>`, `<Tabs>`,
  `<Card>` and `<LinkCard>` from `@astrojs/starlight/components` are themed.

## Adding a playground op

An op is one thing the playground can do: apply a method with some options and
print the matching code. Ops live in `src/components/playground/ops/`. Each file
default-exports an array, and every file in the folder is picked up
automatically, so there's no list to update.

Add your op to the file your area owns (create a new file if none fits). The
comment at the top of `ops/shape.ts` shows the full shape; in short:

```ts
import { defineOp, type ImageSize } from "../types";
import { js } from "../code";

export default [
  defineOp({
    id: "scale", // unique; use the method name
    label: "scale", // tool button text
    icon: "resize", // key in src/components/icons.ts, or raw <svg> inner markup
    group: "shape", // category id
    description: "Scale the width and height by the same factor.",
    controls: [{ type: "slider", key: "f", min: 0.1, max: 2, step: 0.05 }],
    defaults: { f: 0.5 },
    apply: (image, { f }) => {
      image.scale(f);
    },
    code: ({ f }) => `image.scale(${js(f)});`,
  }),
];
```

- **Controls**: `slider`, `number`, `toggle`, `select`, `color` (`"#rrggbb"`),
  `xy` (a point picked by clicking the image) and `rect` (a region dragged on
  the image). Add `when: (opts) => ...` to show a control only sometimes.
- **Defaults** that depend on the image size are a function:
  `defaults: ({ width, height }: ImageSize) => ({ ... })`. Annotate the
  parameter so the option types are inferred.
- **`apply`** mutates the image. It may be async; `ctx.loadImage("file.png")`
  loads a second image from `public/` (for `composite`, `mask`…). Throwing, or
  letting Jimp throw, shows the error in the playground.
- **`code`** returns the statements a reader would write, using a variable named
  `image`. It must produce exactly what `apply` does. Use `js()` to format
  values and `raw("ResizeStrategy.BICUBIC")` for identifiers; list extra named
  imports with `imports: (opts) => ({ jimp: ["ResizeStrategy"] })`.
- **`thumbnail`**: options to use for the sticker on `/methods/`, or `false` to
  show the icon instead.
- Keep ops fast on a 360 × 270 image; the playground re-runs them as sliders move.

## Links

The site is served under `/jimp/`. Link pages with absolute paths that include
it and end with a slash: `/jimp/methods/blur/`, `/jimp/guides/browser/`,
`/jimp/concepts/compositing/#blend-modes`. Method page slugs are kebab-case
(`scaleToFit` → `/jimp/methods/scale-to-fit/`); see `src/data/methods.ts`.

## Light and dark

Both themes are built from the tokens in `src/styles/tokens.css`. Content
shouldn't need colors; if a component does, use the `--jp-*` variables (for
example `var(--jp-text)`, `var(--jp-surface)`, `var(--jp-line)`) rather than
hex values, and check the page in both themes with the switch in the header.

## Checking your work

From `packages/docs`:

```sh
npx astro check   # type-checks .astro, .ts and .tsx (must report 0 errors)
npx astro build   # builds the site, the type reference and the search index
npx astro preview # serves dist/ at http://localhost:4321/jimp/
```

`pnpm build` runs check and build together, as CI does. Search only works in
the built site, not in `astro dev`.

Before you finish, open your page in the preview, in light and dark: run every
playground on it, follow every link and confirm each code sample matches the
current API.
